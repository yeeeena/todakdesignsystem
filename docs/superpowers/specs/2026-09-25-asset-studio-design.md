# 토닥 에셋 스튜디오 설계

2026-09-25 · 상태: 사용자 검토 대기

## 1. 목적

토닥토닥 에셋을 내부 디자이너 몇 명이 함께 관리하는 관리자 페이지를 만든다.

* 지금 쓰는 에셋을 한눈에 본다.
* 주제를 정하면 신마다 아이템을 고르고, 그 아이템에 맞춰 신별 에셋을 새로 생성해 후보로 쌓는다.
* 다른 곳에서 만든 이미지도 후보로 올린다.
* 후보 중 하나를 확정하면 라이브러리, 프로토타입(GitHub main), Figma 원본에 반영된다.

독립 서비스가 아니다. 서버, 배포, 로그인을 직접 만들지 않는다.

## 2. 결정 사항

* 형태: Claude 아티팩트(claude.ai 비공개 페이지). 조직 안에서 링크를 받은 사람만 연다.
* 생성 범위: 신별 세트 전체. 신 6명 × 에셋 10종 = 60칸.
* 생성 모델: 여러 개 중 골라 쓴다. 보는 사람 본인의 Higgsfield 또는 Krea 커넥터로 부르고, 두 서비스 안의 모델을 고를 수 있다.
* 외부 이미지: 칸에 직접 올리기와 여러 장 끌어놓기(파일명 자동 매칭)를 둘 다 지원한다.
* 후보는 GitHub에 올리지 않는다. 확정한 것만 올린다.
* GitHub 반영: main에 바로 커밋한다. 사용자의 작업 폴더가 아닌 main 전용 git worktree에서 한다.
* GitHub·Figma 반영 시점: 페이지에서 확정하면 저장소에 표시만 하고, 실제 반영은 Claude Code의 "동기화"가 한다. 수동("동기화해줘") 또는 예약 작업.
* 새 칸(신 추가, 에셋 종류 추가)은 이번 범위에서 뺀다. 60칸 교체만 한다.

## 3. 칸(슬롯) 목록

신 id: sansin(산신), yongwang(용왕), chilseong(칠성신), samsin(삼신할미), seonang(서낭신), munsin(문신).

에셋 10종과 경로. 크기는 초기 적재 때 원본에서 읽어 칸마다 기록한다. 투명 여부는 원본의 알파 채널로 판정하지 않고 아래 고정 목록으로 정한다(부적·결과 배경도 알파 채널은 있다)(아래 값은 산신 기준 예시).

* 캐릭터: `prototype/assets/deities/{한글이름}.png` · 288×288 투명
* 로딩: `prototype/assets/loading/{id}.png` · 608×608 투명
* 결과 배경: `prototype/assets/result-bg/{id}@2x.png` · 780×1936
* 결과 미리보기: `prototype/assets/result-peek/{id}.png` · 556×596 투명
* 단계 04·05·06: `prototype/assets/steps/{id}-0{4,5,6}@2x.png` · 780×약 790
* 부적 앞·뒤: `prototype/assets/talisman/{id}-{front,back}.png` · 1264×1992
* 부적 카드: `prototype/assets/talisman-card/{id}@2x.png` · 632×996

투명 칸은 캐릭터, 로딩, 결과 미리보기 18칸이다. 부적 앞·뒤는 둥근 모서리만 투명해서 불투명 칸으로 보고, 규격 맞추기 때 원본의 모서리 알파를 그대로 입힌다.

보기만 하고 생성·교체 대상에서 빼는 것: `shelf/mask-*.svg`, `steps/common-*`, `landing-screen@2x.png`, `deities-screen@4x.png`, `loading-bg/`.

## 4. 화면

목업(대화 중 공유)과 같다.

1. 에셋 보기: 6×10 격자. 칸마다 현재 채택본, 후보 있음 표시, Figma 반영 대기 표시. 칸을 누르면 후보와 이력.
2. 새 주제: 주제와 분위기 메모를 넣고 아이디어를 받는다. 지난 주제 목록.
3. 아이템 고르기: 신마다 Claude가 제안한 아이템 3개 중 하나를 고르거나 직접 적는다. 다시 제안받기.
4. 생성: 모델, 범위(세트 전체 또는 일부 칸), 칸당 장수(기본 2장)를 고르면 총 장수와 예상 비용(커넥터가 알려주는 경우)이 표시된다. 신별 진행 막대.
5. 가져오기: 파일 업로드, 파일명으로 칸 자동 매칭, 출처(Midjourney, 직접 그림, 외주, 기타), 주제 연결(선택).
6. 후보 보드: 주제별, 신별로 칸마다 원본과 후보를 나란히 본다. 채택 후보 표시, 그 칸만 다시 생성.
7. 확정: 원본 규격으로 자르기(위치 조정), 규격 검사, 같은 주제의 다른 칸 함께 확정. 확정 후 라이브러리, GitHub, Figma 상태를 칸마다 표시.

페이지 모양은 토닥토닥 제품 화면이 아니라 내부 도구다. 신 이미지가 잘 보이도록 중립 톤으로 만들고 DESIGN.md의 제품 규칙은 적용하지 않는다(사용자 확인 필요).

## 5. 구성

아티팩트 능력(capabilities):

* `db`: 칸, 주제, 후보, 확정 기록.
* `assets`: 원본 사본, 후보 이미지(파일당 20MB 이하).
* `user`: 만든 사람, 확정한 사람.
* `sample`: 주제별 아이템 아이디어.
* `mcp`: Higgsfield `generate_image`·`media_upload`, Krea `generate_image`·`get_job`·`get_upload_url`. 정확한 도구 목록은 시험 후 확정한다.

페이지 소스는 레포의 `tools/asset-studio/index.html`에 두고, 동기화 절차는 `tools/asset-studio/SYNC.md`에 적는다. 파일 교체와 검사는 `tools/asset-studio/sync.py`가 한다.

## 6. 데이터

* `slots/{deity}-{kind}`: 경로, 규격(가로, 세로, 투명 여부), 현재 에셋 id, 현재 git blob SHA, 버전 번호, 이력(에셋 id, 확정 id 목록).
* `topics/{id}`: 주제, 분위기 메모, 신별 아이디어와 고른 아이템, 만든 사람, 만든 때.
* `candidates/{id}`: 칸, 주제(없을 수 있음), 원본 에셋 id, 최종 에셋 id(자르기·배경 제거를 거쳐 규격에 맞춘 PNG), 출처(생성이면 모델과 프롬프트, 업로드면 출처 메모와 원래 파일명), 만든 사람, 상태(후보, 채택 후보, 확정, 버림), 자르기 값.
* `confirmations/{id}`: 확정 한 번의 묶음. 확정한 사람, 때, 되돌리기 여부, 항목 목록. 항목은 칸 하나마다 하나이고 후보 id와 칸별 동기화 상태를 가진다(GitHub: 대기·완료·실패·대체됨과 이유, Figma: 대기·완료·실패). 묶음에는 커밋과 번들 SHA를 적는다.

## 7. 흐름

생성: 고른 아이템과 칸 종류로 프롬프트를 만들고, 그 칸의 현재 원본을 참고 이미지로 넘긴다. 결과를 받아 `assets`에 저장하고 후보로 기록한다.

업로드: 파일을 `assets`에 올리고 후보로 기록한다. 파일명 매칭: 폴더째 끌어놓으면 `폴더/파일명`이 레포 경로와 같을 때 맞춘다. 파일명만 있으면 하나로 정해지는 것만 맞춘다(`산신.png`는 캐릭터, `sansin-front.png`는 부적 앞, `sansin-04@2x.png`는 단계 04). `sansin.png`(로딩·결과 미리보기)와 `sansin@2x.png`(결과 배경·부적 카드)는 여러 칸에 걸리므로 사람이 칸을 고른다. 나머지는 매칭 안 됨으로 둔다.

규격 맞추기: 페이지가 캔버스로 자르고 줄여 최종 PNG를 만들어 `assets`에 저장한다. 투명 칸의 생성 후보는 배경 제거(Higgsfield `remove_background`)를 자동으로 거친다. 배경 제거가 안 되면 그 칸은 업로드로만 확정한다. `sync.py`는 반영 직전에 크기와 투명 여부를 다시 검사만 한다.

확정: 최종 PNG가 규격 검사를 통과한 후보만 확정할 수 있다. 확정하면 칸의 현재 에셋과 버전을 바꾸고, 칸마다 GitHub·Figma 대기 항목을 만든다.

동기화(Claude Code):
Claude Code는 `ArtifactData`로 `db`를 읽고 쓰며, `Artifact` read(path에 에셋 id)로 최종 PNG를 받는다.

1. main 전용 worktree를 최신으로 맞춘다.
2. GitHub 대기 항목을 모두 읽는다. 같은 칸에 대기 항목이 여럿이면 가장 나중 것만 반영하고 나머지는 대체됨으로 둔다.
3. 칸마다 `slots`의 git blob SHA가 레포와 같은지 확인한다. 다르면(누가 레포에서 직접 바꾼 경우) 그 항목만 실패로 두고 알린다.
4. 최종 PNG를 같은 경로에 덮어쓰고 확정 묶음 하나당 커밋 하나를 만든다. 메시지 첫 줄: `에셋 확정: 추석 — 산신 부적 앞·부적 뒤 외 1칸 (확정한 사람)`, 본문에 칸 목록.
5. main에 푸시하고 반영한 칸마다 `slots`의 git blob SHA를 새 값으로 갱신한다.
6. `python3 tools/build_bundle.py`로 번들 SHA를 얻는다.
7. Figma 원본의 해당 이미지를 교체한다.
8. 항목과 묶음에 상태, 커밋, SHA를 적는다. 사용자에게 새 SHA와 "문구 관리 문서 해시 갱신 필요"를 알린다.

되돌리기: 칸 단위다. 칸 이력에서 이전 버전을 고르면 그 에셋으로 칸 하나짜리 새 확정 묶음을 만든다. 기록은 지우지 않는다.

초기 적재: Claude Code에서 원본 60장을 `assets`에 올리고 `slots` 60개를 채운다.

## 8. 오류 처리

* 커넥터 미연결: 생성 버튼 자리에 "Higgsfield 또는 Krea를 연결하세요" 안내. 보기, 업로드, 확정은 된다.
* 생성 실패: 그 칸만 실패로 표시하고 다시 시도 버튼. 한도·잔액 부족은 메시지 그대로 보여준다.
* 규격 불일치: 확정 버튼 대신 무엇이 틀렸는지 보여준다.
* 동시 확정: 같은 칸을 두 사람이 확정하면 나중 확정이 이긴다(동기화 2단계). 이력에 둘 다 남는다.
* 동기화 실패: 확정 기록에 실패와 이유를 남기고 페이지에 표시한다. 다음 동기화 때 다시 시도한다.

## 9. 먼저 시험할 것

구현 첫 단계. 결과에 따라 7장의 생성, 규격 맞추기, 동기화 6~7단계와 예약 여부가 바뀐다.

1. 참고 이미지 전달: 비공개 레포라 원본 주소를 외부에 줄 수 없다. 페이지에서 Higgsfield `media_upload`나 Krea 업로드로 원본을 보낼 수 있는지 확인한다. 안 되면 초기 적재 때 원본을 생성 서비스에 올려 두고 그 id를 칸에 기록한다(계정 단위라면 Krea의 공개 에셋 주소를 쓴다).
2. 결과 받기: 생성 결과 이미지를 페이지에서 받아 `assets`에 저장할 수 있는지 확인한다. 안 되면 결과 주소만 기록하고 동기화 때 Claude Code가 받는다.
3. 배경 제거: 투명 칸 생성 결과에 Higgsfield `remove_background`를 페이지에서 부를 수 있는지 확인한다.
4. Figma 교체: 원본 72장 노드와 60칸의 대응을 확인하고, 이미지 교체가 되는지 확인한다.
5. 예약 동기화: 예약 작업에서 git push와 Figma 교체가 사람 없이 도는지 확인한다. 안 되면 수동 동기화만 둔다.
6. 용량: 부적 원본(1264×1992) 크기의 PNG를 올리고 받는 시간이 쓸 만한지 본다.

## 10. 구현 순서

시험 → 초기 적재와 에셋 보기 → 업로드와 확정 → 동기화 → 주제·아이템·생성. 앞 단계만으로도 쓸 수 있게 만든다.

## 11. 범위 밖

새 신이나 새 에셋 종류 추가, 화면 코드(`todaktodak-working.html`) 수정, 공유용 단일 파일 배포, 권한 단계 나누기(보기 전용 역할).

## 12. 확인 방법

* 초기 적재 후 60칸이 원본과 같은 크기로 보이는지.
* 신 하나로 주제부터 확정까지 한 번, 업로드부터 확정까지 한 번 돌린다.
* 동기화 후 main 커밋, 프로토타입 프리뷰(390·360 폭, 해당 신), Figma 원본, 새 번들 SHA를 확인한다.
* 되돌리기 한 번.
